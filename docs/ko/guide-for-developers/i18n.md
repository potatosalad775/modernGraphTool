UI 문자열은 **Paraglide JS**를 거칩니다. 빌드 시점에 `messages/<locale>.json`을 타입이 있는 함수로
컴파일합니다.

```ts
import * as m from '#lib/paraglide/messages.js';
m.some_key();
```

이는 _운영자용_ 다국어 설정 값(`DESCRIPTION`, `TOPBAR.TITLE`, …)과는 별개입니다. 후자는 런타임에
`resolveI18nValue()`가 해석합니다.

## 규칙 \{#rules\}

- 키 형식은 `밑줄_구분`입니다. `menu.graphPanel`이 아니라 `menu_graph_panel`입니다.
- `src/lib/paraglide/`의 생성된 코드는 **절대** 손으로 수정하지 않으며, gitignore 대상입니다.
- 로케일은 `project.inlang/settings.json`(`baseLocale` + `locales`)에 등록합니다. Vite 플러그인이
  개발·빌드·테스트 시 `src/lib/paraglide/`를 다시 생성합니다.
- 언어 전환은 `#lib/paraglide/runtime.js`의 `setLocale('ko')`로 합니다(`getLocale`, `locales`도 함께
  제공됩니다).

:::tip[영어가 아닌 로케일에 키가 빠져 있어도 괜찮습니다]
Paraglide 컴파일러가 키 단위로 `baseLocale`(`en`)로 자동 폴백합니다. 빌드 오류도, 런타임 크래시도
없습니다. 기여자는 일부만 번역해도 되며, 번역되지 않은 문자열은 누군가 채워 넣을 때까지 그냥 영어로
표시됩니다.
:::

`npm run check`는 Vite를 거치지 않으므로, 갓 클론한 상태에서는 `#lib/paraglide/*`에 타입 선언이
없습니다. 그래서 `check`는 먼저 `npm run i18n:compile`을 실행합니다. Vite 플러그인과 동일한 옵션을
쓰는 Paraglide CLI이므로 둘을 같은 상태로 유지하세요. `prepare`도 이를 실행하므로, 단순히 `npm ci`만
해도 타입 검사가 가능한 트리가 됩니다.

활성 로케일은 `localStorage` → `preferredLanguage` → `baseLocale` 전략으로 정해집니다. 저장된 선택이
우선이고, 그다음은 브라우저의 선호 언어, 마지막은 `en`입니다.

## 키 추가하기 \{#adding-a-key\}

1. 기준이 되는 `messages/en.json`에 키를 추가합니다. 다른 로케일도 번역할 수 있다면 함께 추가하고,
   아니라면 그대로 두세요. 영어로 폴백됩니다.
2. `npm run dev`(또는 `build`)를 실행합니다. Vite 플러그인이 메시지 함수를 다시 생성합니다.
3. `m.your_new_key()`로 사용합니다.
4. `npm run i18n:missing`을 실행해 번역 스테이징 파일에 새 키를 반영합니다.

## 언어 추가하기 \{#adding-a-language\}

보통은 기여자가 Fink의 **Settings** 탭에서 직접 추가하며, 로케일은 번역 PR에 함께 들어옵니다.
[번역하기](./translating.mdx#adding-a-new-language)를 참고하세요. 직접 추가하려면:

1. `project.inlang/settings.json`의 `locales`에 로케일 코드를 추가합니다.
2. `messages/<locale>.json`을 만듭니다. `{ "$schema": "..." }`만 있어도 되며, 나머지는 영어로
   폴백됩니다.
3. `npm run i18n:missing`을 실행해, 아직 번역할 키를 모두 담은
   `messages/_missing_translations_<locale>.json`을 생성합니다.

이것으로 끝입니다. `MiscPanel`의 언어 선택기가 `locales`를 읽고 `Intl.DisplayNames`로 이름을 붙이므로
컴포넌트를 수정할 필요가 없고, 브라우저가 그 언어를 선호하는 방문자에게는 자동으로 선택됩니다. 로케일
코드가 `locales` 항목과 `messages/<locale>.json` 파일 이름을 잇는 유일한 연결고리이니 둘을 똑같이
유지하세요. 이름을 직접 지정하려면 `MiscPanel.svelte`의 `localeLabel`에 코드 → 이름 재정의를
추가하세요.

## 번역 기여 흐름 \{#translation-contribution-flow\}

들어오는 길은 두 가지이고, 둘 다 평범한 풀 리퀘스트로 끝납니다.

**Fink(주 경로).** [Fink](https://fink.inlang.com)는 GitHub에서 `project.inlang`을 바로 열기 때문에
저장소에 따로 설정할 것이 없습니다. 번역자는 브라우저에서 `messages/<locale>.json`을 수정하고, Fink가
저장소를 포크한 뒤 GitHub의 PR 페이지를 열어 줍니다. 번역자용 안내는 [번역하기](./translating.mdx)에
있습니다. 메인테이너가 받게 되는 것은 다음과 같습니다.

- 바뀐 로케일 파일만, 그 안에서도 수정된 메시지만 바뀝니다. Fink는 나머지 줄을 바이트 단위로 그대로
  두고, 빈 번역은 `""`로 쓰지 않고 삭제합니다.
- 기여자가 언어를 추가했다면 `project.inlang/settings.json` 변경도 함께 들어옵니다.
- Fink가 복수형을 직접 다루므로, 복수형은 이미 Paraglide의 variant 형식입니다.

병합한 뒤에는 `npm run i18n:missing`을 실행해, 방금 번역된 키가 스테이징 파일에 남지 않게 하세요.
스테이징 값이 손대지 않은 영어 원문인 동안에는 `i18n:apply`가 어차피 그 키를 건너뛰지만, 오래된
파일은 다음 오프라인 번역자를 헷갈리게 합니다.

**스테이징 파일(오프라인 대안).** 텍스트 편집기로 작업하고 싶은 기여자를 위한 방법입니다.
`messages/<locale>.json`은 그대로 두고, 아직 작업이 필요한 키만 담긴 생성된 스테이징 파일을
수정합니다.

| 명령어                 | 대상       | 설명                                                                                                     |
| ---------------------- | ---------- | -------------------------------------------------------------------------------------------------------- |
| `npm run i18n:check`   | 누구나     | 로케일별로 누락되거나 오래된 키를 보고합니다. 아무것도 변경하지 않습니다.                                |
| `npm run i18n:missing` | 메인테이너 | `messages/_missing_translations_<locale>.json`을 생성합니다. 빠진 키를 `en` 원문으로 채워 둡니다.        |
| `npm run i18n:apply`   | 메인테이너 | 스테이징 파일을 `messages/<locale>.json`에 병합하고(`en` 키 순서로) 스테이징 파일을 삭제합니다.          |

1. `messages/en.json`에 키가 추가되면 → `npm run i18n:missing`으로 스테이징 파일을 다시 생성합니다.
2. 번역자가 `messages/_missing_translations_ko.json`을 수정하고 PR을 엽니다. 확신이 서지 않는 키는
   아예 빼도 됩니다. 그런 키는 계속 영어로 폴백됩니다.
3. PR을 병합한 뒤 `npm run i18n:apply`를 실행하고 결과를 커밋합니다.

`i18n:apply`는 `en.json`에 없는 키와 비워 둔 키를 건너뛰며, 오래된 키는 제거하지 않고 보존합니다.
`en.json`이 넘기지 않는 `{placeholder}`를 쓰는 키, 그리고 로케일에 이미 있는 복수형을 일반 문자열로
덮어쓰게 되는 키도 건너뜁니다(후자는 `--force`로 무시할 수 있습니다). 미리 확인하려면 `--dry-run`을
사용하세요.

### 복수형 \{#plurals\}

숫자를 세는 문장은 `{count} band(s)`로 때우지 않습니다. `en`도 1 band와 2 bands를 구분하고, 1, 2–4,
5 이상에 각기 다른 단어가 필요한 언어도 많습니다. `en.json`의 개수 표현도 `(s)` 대신 복수형으로
씁니다. 스테이징 파일은 두 가지 간단한 형식을 받으며, `i18n:apply`가 이를 Paraglide의
[variant 형식](https://inlang.com/m/gerre34r/library-inlang-paraglideJs/variants)으로 펼칩니다.

```json
{
	"eq_constraint_fit": {
		"=0": "No bands to fit",
		"one": "Fit {count} band",
		"other": "Fit {count} bands"
	},
	"crosssite_search_truncated": "Showing {count} of {total, plural, one {# match} other {# matches}}."
}
```

- **문장 단위 객체**: 복수형마다 키 하나. `{count}`를 셉니다. 다른 입력값을 세려면
  `"plural": "total"`을 추가하세요.
- **인라인 조각**: 문자열 안에 쓰는 ICU 문법으로, `#`이 숫자를 뜻합니다. 한두 단어만 바뀔 때나
  메시지에 카운터가 둘일 때 쓰세요. 모든 조합은 스크립트가 대신 작성합니다.

형식 이름은 로케일의
[CLDR 복수 범주](https://www.unicode.org/cldr/charts/latest/supplemental/language_plural_rules.html)
(`zero`, `one`, `two`, `few`, `many`, `other`)이며 `other`는 필수입니다. 각 스테이징 파일의 `@@info`에
해당 로케일이 쓰는 형식이 적혀 있고, 로케일에서 선택될 일이 없는 형식은 `i18n:apply`가 경고와 함께
버립니다. `"=0": "No bands"` 같은 정확한 숫자는 범주보다 우선하지만 Paraglide 2.27.0 이상이 필요합니다.
그보다 낮으면 `i18n:apply`가 해당 키를 건너뜁니다.

`en.json`에 이미 있는 복수형은 스테이징 파일에 객체 형식으로 나타납니다. 서수나 성별처럼 간단한
형식으로 표현할 수 없는 것은 Paraglide의 전체 배열 형식으로 쓰면 그대로 통과합니다. 파싱 코드는
[scripts/i18n-plural.js](https://github.com/potatosalad775/modernGraphTool/blob/main/scripts/i18n-plural.js)에
있습니다.

Paraglide는 `_missing_translations_*.json`을 무시합니다. `project.inlang/settings.json`에 나열된
로케일만 컴파일합니다.

## Frequency Tutorial 텍스트 \{#frequency-tutorial-text\}

[Frequency Tutorial](../features/frequency-tutorial.mdx) 오버레이의 라벨은 일반 UI 문자열입니다.
대역마다 `_name` / `_desc` 한 쌍이 있으며, 키 이름은 `tutorial_freq_<band>_name`과
`tutorial_freq_<band>_desc`입니다. 대역은 `sub_bass`, `bass`, `lower_mids`, `upper_mids`,
`presence`, `brilliance`입니다.

```json
{
	"tutorial_freq_sub_bass_name": "Sub Bass",
	"tutorial_freq_sub_bass_desc": "The Rumble, usually out of human's hearing range...",
	"tutorial_freq_bass_name": "Bass",
	"tutorial_freq_bass_desc": "Determines how 'fat' or 'thin' the sound is..."
}
```

번들에 컴파일되어 들어가므로 CDN이나 사전 빌드 릴리스로 운영하는 경우에는 바꿀 수 없습니다. 문구를
고치려면 소스에서 빌드하거나 PR을 보내야 합니다.

:::note
`messages/en.json`에서 키를 추가·이름 변경·삭제한 뒤에는 `npm run i18n:check`를 실행하세요. 정보
제공용이며 빌드를 막지는 않지만, 그 변경이 번역자에게 얼마나 부담을 주는지 가장 빠르게 확인하는
방법입니다.
:::
