# Build & Deployment Internals

How the three build outputs are produced. If you only want to *deploy* modernGraphTool, see [Guide for Operators → Choosing a Deployment](/modernGraphTool/docs/guide-for-admins/setup-env/) instead — this page is about how the build itself works. ## Outputs | Command | Output | What it is | | ----------------------------- | --------------------- | ----------------------------------------------------- | | `npm run build` | `dist/` | Static SPA, prerendered, SPA fallback via `.htaccess` | | `npm run build:cdn` | `dist-cdn/` | Thin loader for jsDelivr-hosted assets | | `npm run build:site-template` | `dist-site-template/` | The GitHub Pages template repo | The CDN build emits a thin `cdn-index.html` loader plus `cdn/loader.js`; set `MGT_CDN_BASE` to rewrite the `_app/` URLs. ## The `defaults/` mechanism A Vite plugin serves `defaults/` as a fallback during development and copies its contents into `dist/` at build time — **without** overwriting files that already exist under `static/`. That is how an operator’s local customizations survive an upgrade. Files an operator is expected to edit in `dist/`: `config.js`, `theme.css`, `data/`, `assets/strings/`. Caution **Never import from `static/` or `defaults/` as modules.** `fetch()` them at runtime. They are operator-editable deployment artifacts, not build inputs — importing one bakes a copy into the bundle and the operator’s edit silently stops taking effect. ## GitHub Pages template [potatosalad775/modernGraphTool_site](https://github.com/potatosalad775/modernGraphTool_site) is a separate repository that operators copy with “Use this template”. It is **generated output, not a hand-maintained repo.** `npm run build:site-template` assembles it, and `.github/workflows/sync-site-template.yml` force-syncs the result on every push to `main` that touches `defaults/`, `site-template/`, or the script. Edit the sources in the main repo — anything committed straight to the template repo is overwritten on the next sync. * Most of it is `defaults/` verbatim (`theme.css`, `data/`, `assets/`), which is the whole reason the sync exists — that content drifts the moment `defaults/` changes. * `config.js` is `defaults/config.js` with the commented `CDN_MODE` stub spliced out and `site-template/config-cdn-mode.js` spliced in, so new config options reach the template for free. The splice is anchored on the stub’s first and last lines and **throws** if it stops matching — a template with no live `CDN_MODE` is a blank page, since its `index.html` is only a loader. That file is a JS *fragment*, so it sits in `.prettierignore` and ESLint’s ignores; the generated `config.js` is syntax-checked by the build script instead. * `site-template/index.html` is source, **not** derived from `cdn/cdn-index.html` — keep the shared parts in sync by hand. Two deliberate divergences: 1. It always loads `loader.js` from jsDelivr (no localhost branch — operators never iterate on the loader). 2. It carries an inline base-path detector that sets `CDN_MODE.BASE_PATH` from the first path segment on `*.github.io` hosts, so both `username.github.io/<repo>/` and `username.github.io/` work with no config edit, and a repo rename survives. It defers to an explicit `BASE_PATH`. This lives in the template rather than in `cdn/loader.js` because a loader change only reaches deployments after the next `cdn` branch publish. * The workflow needs a `SITE_TEMPLATE_TOKEN` secret (fine-grained PAT, `Contents: write` on the template repo) — `GITHUB_TOKEN` cannot push across repositories.

# Contributing

> Setting up modernGraphTool locally, the code style CI enforces, and how to open a pull request.

Contributions are always welcome, no matter how small or large. This page covers what you need before your first pull request; the [Overview](/modernGraphTool/docs/guide-for-developers/overview/) has the architecture and project layout. ## What to contribute * **Bug fixes** — always welcome. * **Accessibility improvements** — the target is WCAG AAA. * **Translations** — no code required. See the [translation flow](/modernGraphTool/docs/guide-for-developers/i18n/#translation-contribution-flow). * **Documentation** — typo fixes, clarifications, new guides. The sources live in `docs/src/content/docs/`. * **Features** — please [open an issue](https://github.com/potatosalad775/modernGraphTool/issues) first to discuss the approach. ## Setup You need [Node.js](https://nodejs.org/) 24 or later (CI runs the latest 24.x) and npm, which ships with it. 
```bash
git clone https://github.com/potatosalad775/modernGraphTool.git
cd modernGraphTool
npm install
npm run dev        # http://localhost:5173
```
 To run `npm run lint`, also install the docs site’s dependencies once with `cd docs && npm ci`. The root lint reaches files under `docs/`, and ESLint resolves their config through `docs/tsconfig.json`, which cannot load without `docs/node_modules`. ## Code style **Prettier** and **ESLint** are authoritative: tabs, single quotes, no trailing commas, 100-character lines. 
```bash
npm run lint       # check
npm run format     # fix
```
 CI runs `npm run lint` on Linux and Windows, so a PR that is not Prettier-clean will not merge. ### Line endings Every text file is **LF**, pinned by `.gitattributes`. That overrides `core.autocrlf`, which the Git for Windows installer turns on by default, so there is nothing to configure locally. Just don’t commit CRLF. `.editorconfig` tells your editor the same thing; install the EditorConfig extension if your editor doesn’t read it natively. ### git blame One commit reformatted the whole repository. To keep `git blame` pointing at real authorship rather than that commit, run this once per clone: 
```bash
git config blame.ignoreRevsFile .git-blame-ignore-revs
```
 GitHub’s blame view already honours the file. ## Svelte 5 conventions The project uses **Svelte 5 runes**, enforced globally: | Use | Don’t use | | ------------------------- | ----------------- | | `let x = $state(value)` | `writable(value)` | | `let y = $derived(expr)` | `$: y = expr` | | `$effect(() => { ... })` | `afterUpdate` | | `let { prop } = $props()` | `export let prop` | Stores are reactive class instances in `.svelte.ts` files, not plain `.ts`. Most directories under `src/lib/` have an `AGENTS.md` with the rules specific to that area; read it before changing code there. ## Shared components Build UI out of the wrappers in `src/lib/components/atoms/`, such as `Button`, `Input`, `Switch`, `Accordion`, `PopoverPanel`, `ScrollArea` and `Skeleton`, rather than the bare HTML element. They carry the focus-visible ring, the transition, the disabled styling and the operator-customizable palette. A raw `<button>` quietly opts out of all of that and drifts as themes change. * `Button` takes `variant` and `size` props instead of a class list. Check whether a size already covers what you need (`toolbar`, `icon`, `icon-sm`, `icon-xs`) before writing padding classes by hand. Its required `title` also becomes the `aria-label`, so keep the title and the visible text saying the same thing. * Anything passed to `Button` in `class` is merged with [tailwind-merge](https://github.com/dcastil/tailwind-merge), so an override beats the built-in style **without** a `!` modifier: write `class="rounded-full"`, not `class="rounded-full!"`. On a raw element, conflicting utilities tie on specificity and `!` is still needed. * Checkboxes and radios are the exception. No atom covers them, so they stay raw. Elements bits-ui owns through a `child` snippet stay as bits-ui renders them. Colors always go through the semantic tokens (`bg-base-100`, `text-base-content/60`, `text-primary`, …), never a literal palette value like `text-zinc-500`, so that operator themes stay coherent. ## Pull requests 1. **Branch** from `main`, and keep each PR to a single concern. 2. **Run the checks** before pushing: 
   ```bash
   npm run check    # TypeScript + Svelte type checking
   npm run lint     # ESLint + Prettier
   npm run test     # all tests
   ```
 CI runs exactly these on Linux and Windows, plus builds of the app, the CDN distribution and the docs site. See [Testing](/modernGraphTool/docs/guide-for-developers/testing/) for the two test projects and the coverage ratchet. 3. **Update the docs** in the same PR when a change affects what users see, what operators configure, or how developers contribute. 4. **Open the PR** with a clear description of what changed and why. Keep commit messages short; the reasoning belongs in the PR description. By contributing, you agree that your contributions will be licensed under the [MIT License](https://github.com/potatosalad775/modernGraphTool/blob/main/LICENSE).

# Internationalization

UI strings go through **Paraglide JS**, which compiles `messages/<locale>.json` into typed functions at build time. 
```ts
import * as m from '#lib/paraglide/messages.js';
m.some_key();
```
 This is separate from the *operator-facing* multilingual config values (`DESCRIPTION`, `TOPBAR.TITLE`, …), which are resolved at runtime by `resolveI18nValue()`. ## Rules * Key format is `underscore_separated` — `menu_graph_panel`, not `menu.graphPanel`. * Generated code in `src/lib/paraglide/` is **never** hand-edited, and is gitignored. * Locales are registered in `project.inlang/settings.json` (`baseLocale` + `locales`). The Vite plugin regenerates `src/lib/paraglide/` on dev, build and test. * Switch language with `setLocale('ko')` (also `getLocale`, `locales`) from `#lib/paraglide/runtime.js`. `npm run check` does **not** go through Vite, so on a fresh clone `#lib/paraglide/*` would have no type declarations. `check` therefore runs `npm run i18n:compile` first — the Paraglide CLI with the same options as the Vite plugin, so keep the two in sync. `prepare` runs it too, so a plain `npm ci` leaves the tree typecheckable. The active locale is resolved by the strategy `localStorage` → `preferredLanguage` → `baseLocale`: a saved choice wins, then the browser’s preferred language, then `en`. ## Adding a key 1. Add the key to `messages/en.json`, the source of truth. Add it to other locales too if you can translate it; otherwise leave them alone and they fall back to English. 2. Run `npm run dev` (or `build`). The Vite plugin regenerates the message functions. 3. Use it as `m.your_new_key()`. 4. Run `npm run i18n:missing` so the translation staging files pick up the new key. ## Adding a language 1. Add the locale code to `locales` in `project.inlang/settings.json`. 2. Create `messages/<locale>.json`. It can hold as little as `{ "$schema": "..." }`; the rest falls back to English. 3. Run `npm run i18n:missing` to generate `messages/_missing_translations_<locale>.json`, listing everything still to translate. That’s it — the `MiscPanel` picker reads `locales` and labels them via `Intl.DisplayNames`, so no component edit is needed, and visitors whose browser prefers the language get it automatically. The locale code is the only link between the `locales` entry and the `messages/<locale>.json` filename, so keep the two identical. For a custom label, add a code → label override to `localeLabel` in `MiscPanel.svelte`. ## Translation contribution flow Translators never touch `messages/<locale>.json` directly. They edit a generated staging file that contains only the keys still needing work: | Command | Who | What it does | | ---------------------- | ---------- | ----------------------------------------------------------------------------------------------------------- | | `npm run i18n:check` | anyone | Reports missing / stale keys per locale. Changes nothing. | | `npm run i18n:missing` | maintainer | Writes `messages/_missing_translations_<locale>.json` — the gap keys, pre-filled with the `en` source text. | | `npm run i18n:apply` | maintainer | Merges those staging files back into `messages/<locale>.json` (in `en` key order) and deletes them. | 1. A key is added to `messages/en.json` → run `npm run i18n:missing` to regenerate the staging files. 2. A translator edits `messages/_missing_translations_ko.json` and opens a PR. Keys they’re unsure about can be left out entirely — those keep falling back to English. 3. After merging the PR, run `npm run i18n:apply` and commit the result. `i18n:apply` skips keys not present in `en.json` and keys left blank, and preserves stale keys rather than dropping them. It also skips a key whose text uses a `{placeholder}` that `en.json` doesn’t pass, and a plain string that would replace a plural already in the locale (`--force` overrides the latter). Use `--dry-run` to preview. ### Plurals A count needs more than `{count} band(s)`: `en` splits 1 band from 2 bands, and many languages need a different word for 1, 2–4 and 5+. Write `en.json` counts as plurals too, never `(s)`. The staging files accept two short forms, and `i18n:apply` expands them into Paraglide’s [variant format](https://inlang.com/m/gerre34r/library-inlang-paraglideJs/variants): 
```json
{
  "eq_constraint_fit": {
    "=0": "No bands to fit",
    "one": "Fit {count} band",
    "other": "Fit {count} bands"
  },
  "crosssite_search_truncated": "Showing {count} of {total, plural, one {# match} other {# matches}}."
}
```
 * **Whole-sentence object** — one key per plural form. It counts `{count}`; add `"plural": "total"` to count another input. * **Inline fragment** — ICU syntax inside the string, with `#` standing for the number. Use it when only a word or two changes, or when a message has two counters: the script writes out every combination, so the translator doesn’t have to. The forms are the locale’s [CLDR plural categories](https://www.unicode.org/cldr/charts/latest/supplemental/language_plural_rules.html) (`zero`, `one`, `two`, `few`, `many`, `other`). `other` is required. Each staging file’s `@@info` lists the forms that locale uses, and `i18n:apply` drops any form the locale never selects, with a warning. An exact number such as `"=0": "No bands"` takes precedence over the categories, but needs Paraglide 2.27.0 or later. Below that, `i18n:apply` skips the key. A plural already in `en.json` appears in the staging file as the object form. Anything the short forms can’t express, such as ordinals or gender, can be written in Paraglide’s full array form, which passes through unchanged. The parsing lives in [scripts/i18n-plural.js](https://github.com/potatosalad775/modernGraphTool/blob/main/scripts/i18n-plural.js). Paraglide ignores `_missing_translations_*.json` — it only compiles the locales listed in `project.inlang/settings.json`. ## Frequency Tutorial text The [Frequency Tutorial](/modernGraphTool/docs/features/frequency-tutorial/) overlay’s labels are ordinary UI strings, one `_name` / `_desc` pair per band, keyed `tutorial_freq_<band>_name` and `tutorial_freq_<band>_desc`, where the bands are `sub_bass`, `bass`, `lower_mids`, `upper_mids`, `presence` and `brilliance`: 
```json
{
  "tutorial_freq_sub_bass_name": "Sub Bass",
  "tutorial_freq_sub_bass_desc": "The Rumble, usually out of human's hearing range...",
  "tutorial_freq_bass_name": "Bass",
  "tutorial_freq_bass_desc": "Determines how 'fat' or 'thin' the sound is..."
}
```
 Because they compile into the bundle, operators on a CDN or pre-built deployment cannot change them — rewording one is a source build, or a PR.

# Guide for Developers

> Architecture, project layout and build commands for contributing to modernGraphTool.

This guide is for working on modernGraphTool itself. To run a database with it, see the [Guide for Operators](/modernGraphTool/docs/guide-for-admins/) instead. Contributions are welcome. This section covers: * **[Contributing](/modernGraphTool/docs/guide-for-developers/contributing/)** — setup, code style, and how to open a pull request. Start here. * **[Testing](/modernGraphTool/docs/guide-for-developers/testing/)** — the two Vitest projects, coverage, and the smoke test. * **[Build & Deployment Internals](/modernGraphTool/docs/guide-for-developers/build-and-deploy/)** — the build outputs and how `defaults/` reaches them. * **[Internationalization](/modernGraphTool/docs/guide-for-developers/i18n/)** — UI strings, adding a language, and the translation flow. ## Tech Stack * **Language**: TypeScript (strict) * **Framework**: SvelteKit 3 + Svelte 5 (Runes) * **Styling**: Tailwind CSS 4 + bits-ui (headless accessible components) * **Graph Rendering**: D3.js (SVG-based) * **i18n**: Paraglide JS (compile-time internationalization) * **Testing**: Vitest, with Playwright browser mode for component specs * **Build Output**: Static SPA via `adapter-static` → `dist/` ## Project Structure 
```plaintext
src/
├── routes/              # SvelteKit routes (single-page SPA) + layout.css (Tailwind entry)
├── lib/
│   ├── components/      # UI: atoms, controls, equalizer, features, graph, layout, panels
│   ├── stores/          # Reactive state as class instances (.svelte.ts)
│   ├── services/        # Data provider, commands, cross-site index, audio, analytics
│   ├── graph/           # D3.js graph engine and overlays
│   ├── device-peq/      # Hardware EQ: connect flow over the eqcaps bridge, push plans
│   ├── workers/         # AutoEQ off the main thread (turboEQ wasm + fallback)
│   ├── utils/           # Parsing, normalization, smoothing, URL encoding, config
│   ├── types/           # TypeScript type definitions
│   └── paraglide/       # Generated i18n functions (do not edit)
└── app.html             # HTML template (loads config.js and theme.css)
defaults/                # Operator-editable config.js, theme.css, sample data
messages/                # Paraglide sources, one JSON file per locale
cdn/                     # CDN deployment templates (thin index.html + loader.js)
scripts/                 # CDN and site-template builds, boot manifest, i18n tooling
site-template/           # Sources for the GitHub Pages template repo
docs/                    # This documentation site (Astro + Starlight)
```
 Most directories under `src/lib/` carry their own `AGENTS.md` with the invariants specific to that area — read it before changing code there. ## Build Commands | Command | Description | | ----------------------------- | -------------------------------------------------------- | | `npm run dev` | Start development server (<http://localhost:5173>) | | `npm run build` | Production build to `dist/` | | `npm run build:cdn` | Build CDN-optimized distribution to `dist-cdn/` | | `npm run build:site-template` | Build the GitHub Pages template to `dist-site-template/` | | `npm run preview` | Preview the built output | | `npm run check` | TypeScript + Svelte type checking | | `npm run test` | Run all Vitest tests | | `npm run lint` | Prettier + ESLint check | | `npm run format` | Auto-format code |

# Testing

modernGraphTool uses **Vitest** with **Playwright browser mode**. Specs are co-located next to the code they cover as `*.spec.ts`. ## Running tests | Command | What it does | | ----------------------- | -------------------------------------------------------- | | `npm run test` | Full suite — both the `client` and `server` projects | | `npm run test:unit` | Same suite in watch mode | | `npm run test:coverage` | Full suite + v8 coverage report into `coverage/` | | `npm run test:smoke` | Boots the built `dist/` in a browser (run `build` first) | ## The two projects The **filename decides which project runs a spec**: * `*.svelte.spec.ts` → the `client` project, in real Chromium via Playwright * everything else → the `server` project, in node Most specs drive stores and services directly. Component specs mount with `render()` from `vitest-browser-svelte` and query through `page.getBy*` from `vitest/browser`. ## Coverage The configuration lives in `vite.config.ts` under `test.coverage`, and two settings there are load-bearing: * **The `include` glob covering all of `src`** is what makes files that no test imports count at all. Without it an untested module vanishes from the denominator rather than showing as the 0% it is — the \~25 device handler and connector modules that lived in `device-peq/` before the eqcaps bridge replaced them made the reported number about 10 points optimistic that way. (Vitest 4 removed the old `coverage.all` flag — `include` now does that job, and passing `all` is a type error.) * **`exclude` omits the Paraglide output.** `src/lib/paraglide/` is generated by the Paraglide Vite plugin and is gitignored; counting it added \~3800 machine-written statements — a third of the total — and dragged the figure well below what the hand-written source actually is. `src/lib/types/**` (type-only) and `src/routes/**` (shells covered by the boot tests) are excluded for the same “not meaningfully coverable” reason. `thresholds` is a ratchet, not a target It holds the measured numbers as of the last improvement. Raise it when coverage goes up; **never lower it to turn a red run green.** CI runs coverage on the Linux leg only, and it blocks — a PR that falls below the ratchet has removed coverage that used to exist. ## Smoke test 
```bash
npm run build && npm run test:smoke
```
 The unit suite mounts components against source, so nothing in it ever loads what the build emits. An adapter-static misconfiguration, a `defaults/` file the Vite plugin stopped copying, an asset-URL regression, or a worker that fails to resolve once bundled will all ship a blank page with the whole suite green. `scripts/smoke-dist.js` serves `dist/` over real HTTP — including the SPA fallback that `.htaccess` provides — boots it in Playwright chromium, and fails on a console error, an uncaught exception, a 4xx, a graph that never draws, or a `?share=` link that lands no curve. Two things to keep in mind when extending it: * **A 200 does not prove a file exists.** The SPA fallback answers anything not on disk with `index.html`, on the real Apache host as much as here, so asset checks compare the body against the HTML shell rather than trusting the status. * It runs in the `build` CI job, after `npm run build`, because it needs the built output. ## Continuous integration `.github/workflows/ci.yml` runs on every PR and every push to `main`: `lint` → `check` → `test` on **both ubuntu-latest and windows-latest**, plus a build of the app, the CDN distribution and the docs site on Linux. The Windows leg is not redundant. Git for Windows sets `core.autocrlf=true` in its system config, so before `.gitattributes` pinned every text file to `eol=lf`, the same commit was Prettier-clean on macOS and dirty on Windows. The **Working tree must be clean** step guards against that regressing: it fails if a checkout plus install leaves anything modified, or if CRLF ever reaches the index. `npm run lint` must exit 0. ESLint *warnings* do not fail the build. Rule overrides live in `eslint.config.js` and each carries a comment explaining why — notably `no-useless-assignment` is off for `*.svelte` because it misreads `$bindable()` prop defaults, and `no-explicit-any` is off under `docs/` because the config migration tool parses arbitrary operator-authored config.
