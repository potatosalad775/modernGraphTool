UI strings go through **Paraglide JS**, which compiles `messages/<locale>.json` into typed functions
at build time.

```ts
import * as m from '#lib/paraglide/messages.js';
m.some_key();
```

This is separate from the _operator-facing_ multilingual config values (`DESCRIPTION`,
`TOPBAR.TITLE`, …), which are resolved at runtime by `resolveI18nValue()`.

## Rules

- Key format is `underscore_separated` — `menu_graph_panel`, not `menu.graphPanel`.
- Generated code in `src/lib/paraglide/` is **never** hand-edited, and is gitignored.
- Locales are registered in `project.inlang/settings.json` (`baseLocale` + `locales`). The Vite
  plugin regenerates `src/lib/paraglide/` on dev, build and test.
- Switch language with `setLocale('ko')` (also `getLocale`, `locales`) from `#lib/paraglide/runtime.js`.

:::tip[Missing keys in a non-English locale are fine]
Paraglide's compiler falls back to `baseLocale` (`en`) per key automatically — no build error, no
runtime crash. Contributors can add partial translations; untranslated strings just render in English
until someone fills them in.
:::

`npm run check` does **not** go through Vite, so on a fresh clone `#lib/paraglide/*` would have no
type declarations. `check` therefore runs `npm run i18n:compile` first — the Paraglide CLI with the
same options as the Vite plugin, so keep the two in sync. `prepare` runs it too, so a plain `npm ci`
leaves the tree typecheckable.

The active locale is resolved by the strategy `localStorage` → `preferredLanguage` → `baseLocale`: a
saved choice wins, then the browser's preferred language, then `en`.

## Adding a key

1. Add the key to `messages/en.json`, the source of truth. Add it to other locales too if you can
   translate it; otherwise leave them alone and they fall back to English.
2. Run `npm run dev` (or `build`). The Vite plugin regenerates the message functions.
3. Use it as `m.your_new_key()`.
4. Run `npm run i18n:missing` so the translation staging files pick up the new key.

## Adding a language

1. Add the locale code to `locales` in `project.inlang/settings.json`.
2. Create `messages/<locale>.json`. It can hold as little as `{ "$schema": "..." }`; the rest falls
   back to English.
3. Run `npm run i18n:missing` to generate `messages/_missing_translations_<locale>.json`, listing
   everything still to translate.

That's it — the `MiscPanel` picker reads `locales` and labels them via `Intl.DisplayNames`, so no
component edit is needed, and visitors whose browser prefers the language get it automatically. The
locale code is the only link between the `locales` entry and the `messages/<locale>.json` filename,
so keep the two identical. For a custom label, add a code → label override to `localeLabel` in
`MiscPanel.svelte`.

## Translation contribution flow

Translators never touch `messages/<locale>.json` directly. They edit a generated staging file that
contains only the keys still needing work:

| Command                | Who        | What it does                                                                                                |
| ---------------------- | ---------- | ----------------------------------------------------------------------------------------------------------- |
| `npm run i18n:check`   | anyone     | Reports missing / stale keys per locale. Changes nothing.                                                   |
| `npm run i18n:missing` | maintainer | Writes `messages/_missing_translations_<locale>.json` — the gap keys, pre-filled with the `en` source text. |
| `npm run i18n:apply`   | maintainer | Merges those staging files back into `messages/<locale>.json` (in `en` key order) and deletes them.         |

1. A key is added to `messages/en.json` → run `npm run i18n:missing` to regenerate the staging files.
2. A translator edits `messages/_missing_translations_ko.json` and opens a PR. Keys they're unsure
   about can be left out entirely — those keep falling back to English.
3. After merging the PR, run `npm run i18n:apply` and commit the result.

`i18n:apply` skips keys not present in `en.json` and keys left blank, and preserves stale keys rather
than dropping them. It also skips a key whose text uses a `{placeholder}` that `en.json` doesn't
pass, and a plain string that would replace a plural already in the locale (`--force` overrides
the latter). Use `--dry-run` to preview.

### Plurals

A count needs more than `{count} band(s)`: `en` splits 1 band from 2 bands, and many languages
need a different word for 1, 2–4 and 5+. Write `en.json` counts as plurals too, never `(s)`. The
staging files accept two short forms, and `i18n:apply` expands them into Paraglide's
[variant format](https://inlang.com/m/gerre34r/library-inlang-paraglideJs/variants):

```json
{
	"eq_constraint_fit": {
		"=0": "No bands to fit",
		"one": "Fit {count} band",
		"other": "Fit {count} bands"
	},
	"crosssite_search_truncated": "Showing {count} of {total, plural, one {# match} other {# matches}}."
}
```

- **Whole-sentence object** — one key per plural form. It counts `{count}`; add
  `"plural": "total"` to count another input.
- **Inline fragment** — ICU syntax inside the string, with `#` standing for the number. Use it when
  only a word or two changes, or when a message has two counters: the script writes out every
  combination, so the translator doesn't have to.

The forms are the locale's
[CLDR plural categories](https://www.unicode.org/cldr/charts/latest/supplemental/language_plural_rules.html)
(`zero`, `one`, `two`, `few`, `many`, `other`). `other` is required. Each staging file's `@@info`
lists the forms that locale uses, and `i18n:apply` drops any form the locale never selects, with a
warning. An exact number such as `"=0": "No bands"` takes precedence over the categories, but
needs Paraglide 2.27.0 or later. Below that, `i18n:apply` skips the key.

A plural already in `en.json` appears in the staging file as the object form. Anything the short
forms can't express, such as ordinals or gender, can be written in Paraglide's full array form,
which passes through unchanged. The parsing lives in
[scripts/i18n-plural.js](https://github.com/potatosalad775/modernGraphTool/blob/main/scripts/i18n-plural.js).

Paraglide ignores `_missing_translations_*.json` — it only compiles the locales listed in
`project.inlang/settings.json`.

## Frequency Tutorial text

The [Frequency Tutorial](../features/frequency-tutorial.mdx) overlay's labels are ordinary UI
strings, one `_name` / `_desc` pair per band, keyed `tutorial_freq_<band>_name` and
`tutorial_freq_<band>_desc`, where the bands are `sub_bass`, `bass`, `lower_mids`, `upper_mids`,
`presence` and `brilliance`:

```json
{
	"tutorial_freq_sub_bass_name": "Sub Bass",
	"tutorial_freq_sub_bass_desc": "The Rumble, usually out of human's hearing range...",
	"tutorial_freq_bass_name": "Bass",
	"tutorial_freq_bass_desc": "Determines how 'fat' or 'thin' the sound is..."
}
```

Because they compile into the bundle, operators on a CDN or pre-built deployment cannot change
them — rewording one is a source build, or a PR.

:::note
Run `npm run i18n:check` after adding, renaming or removing keys in `messages/en.json`. It is
informational and non-blocking, but it is the fastest way to see what a change costs translators.
:::
